# ArchGuard

> **Платформа архитектурного контроля по модели «Политики как код» (Policy-as-Code)**: автоматическая проверка Pull Request на соответствие версионируемым инженерным стандартам, предотвращение деградации архитектуры и предоставление разработчикам практических рекомендаций на основе анализа AST.

## Что такое ArchGuard?

Архитектурная документация в Wiki или Notion часто устаревает, поскольку в процессе быстрого ревью кода разработчикам сложно сверяться со статическими правилами.

**ArchGuard** решает эту проблему, превращая инженерные правила в автоматизированные проверки GitHub Checks:

- **Статический анализ AST**: Использование TypeScript Compiler API для синтаксической инспекции, метрик классов/методов и построения графа зависимостей между слоями.
- **Встроенные аннотации в PR**: Добавление пояснений нарушений, архитектурных обоснований и готовых предложений по исправлению прямо в строки диффа.
- **Индекс архитектурного здоровья (0 - 100)**: Объективная оценка качества PR с возможностью блокировки слияния при наличии критических замечаний.
- **Интерактивная база стандартов**: Полная интеграция с порталом Docusaurus, подробно объясняющим предпосылки каждого правила и способы исправления.
- **Временные исключения с дедлайном**: Декларативное управление техдолгом в `.archstandards/config.yaml` с обязательным указанием причины и срока действия.

## Архитектура системы

```text
  Разработчик создает / обновляет PR
               │
               ▼
   [ Fastify Webhook Сервер ] ── HMAC-SHA256 криптографическая верификация
               │
               ▼
    [ Слой адаптера GitHub ] ─── Получение измененных файлов и diff (Octokit)
               │
               ▼
      [ Ядро ArchGuard ] ─────── AST-парсеры и классификатор файлов
               │
        ┌──────┴──────┐
        ▼             ▼
   [ 18 правил ] [ Исключения ]
        │             │
        └──────┬──────┘
               ▼
     [ Агрегатор находок ] ───── Расчет штрафных баллов и индекса здоровья
               │
               ▼
    [ GitHub Check Run API ] ─── Нативные аннотации и подробный Markdown-отчет
```

## Каталог из 18 встроенных правил

| Категория         | ID правила | Описание стандарта                                                 | Серьезность |
| :---------------- | :--------- | :----------------------------------------------------------------- | :---------- |
| **Архитектура**   | `ARCH-001` | Контроллеры не должны напрямую импортировать репозитории           | `error`     |
|                   | `ARCH-002` | Контроллеры не должны содержать бизнес-логику (>20 строк в методе) | `warning`   |
|                   | `ARCH-003` | Сервисы не должны зависеть от HTTP/веб-фреймворков                 | `error`     |
|                   | `ARCH-004` | Циклические зависимости между модулями запрещены                   | `error`     |
| **Стандарты API** | `API-001`  | Эндпоинты должны валидировать входные данные (Zod, Joi и др.)      | `warning`   |
|                   | `API-002`  | Публичные эндпоинты должны объявлять rate limiting middleware      | `warning`   |
|                   | `API-003`  | POST-методы создания ресурса должны возвращать HTTP 201 Created    | `warning`   |
|                   | `API-004`  | Ответы об ошибках должны соответствовать структуре RFC 7807        | `info`      |
| **Тестирование**  | `TEST-001` | Для новых сервисов обязательно наличие companion-теста             | `error`     |
|                   | `TEST-002` | Сложная бизнес-логика (>15 строк) требует выделенных тестов        | `warning`   |
|                   | `TEST-003` | Репозиторий должен поддерживать баланс тестов не ниже 80%          | `warning`   |
|                   | `TEST-004` | Запрещено отключать тесты (`.skip`, `xit`) ради прохождения CI     | `error`     |
| **Безопасность**  | `SEC-001`  | Исходный код не должен содержать хардкод API-ключей и паролей      | `error`     |
|                   | `SEC-002`  | Запрещен вывод паролей и токенов в логи приложения                 | `error`     |
|                   | `SEC-003`  | Строки подключения к БД должны использовать переменные окружения   | `warning`   |
| **Именование**    | `NAME-001` | Классы и интерфейсы должны использовать PascalCase                 | `info`      |
|                   | `NAME-002` | Функции и методы должны использовать camelCase                     | `info`      |
|                   | `NAME-003` | Булевы переменные должны иметь префиксы (`is`/`has`/`can`)         | `info`      |

## Начало работы

### Системные требования

- Node.js $\ge 20.0.0$
- pnpm $\ge 9.0.0$

### Установка и сборка

```bash
git clone https://github.com/Ashutosh-Yadav-256/ArchGuard.git
cd ArchGuard

pnpm install

pnpm build

pnpm test

pnpm benchmark
```

### Локальный запуск

```bash
pnpm --filter @archstandards/github-app start

pnpm --filter @archstandards/docs start
```

## Конфигурация (`.archstandards/config.yaml`)

```yaml
version: "1.0"

rules:
  include:
    - "*"
  exclude:
    - "NAME-*"

policy:
  fail_on:
    - "error"
  warn_on:
    - "warning"

scoring:
  base: 100
  deductions:
    error: 15
    warning: 5
    info: 1

exceptions:
  - rule: "ARCH-001"
    path: "src/controllers/legacy-export.controller.ts"
    reason: "Direct query optimization required pending database migration."
    expires: "2026-12-31"
```
